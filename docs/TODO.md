> PRD.md를 기반으로 작성된 구현 계획입니다. 할 일 번호("단계-순번")로 서로를 지목합니다.
> **'완료'의 기준**: 코딩이 끝난 것이 아니라 **테스팅까지 통과한 것**을 의미합니다. 그래서 모든 "구현" 항목은 짝이 되는 "테스트" 항목을 가집니다.
> 승인 후, 한 단계가 끝날 때마다 완료한 번호를 나열해 보고하고 확인받은 뒤 다음 단계로 넘어갑니다.
> PRD 개편(확장 1)으로 멜로디 모드 기능 번호가 #4-n → #4-A-n으로 바뀌었습니다. 1~6단계의 "PRD #4-n"은 "#4-A-n"으로 읽습니다.

# 확장 4 — 내 악보 (직접 입력) (완료)

> PRD #4-E. 상단 탭에 [내 악보]를 더한다. 사용자가 악보를 직접 입력해 브라우저에 저장하고, 그 악보를 2마디씩 구간으로 나눠 음높이 받아 적기로 연습한다. 받아 적기·채점은 멜로디 모드를, 음표 그림·길이 규칙은 리듬 모드를, 음높이 좌표·오선 입력은 오선(staff.js)을 다시 쓰고, 악보 보기(음높이 + 길이)·편집기·저장소는 새로 만든다.

# 확장 6 — MusicXML 불러오기

> PRD #4-G. MuseScore 등에서 내보낸 MusicXML(.musicxml/.xml/.mxl)을 불러와, 고른 한 성부를 **곡을 바꾸지 않고** 확장 5 형식(v2)으로 옮겨 담는다. 연습은 확장 5와 같이 음높이만 받아 적는다.
> 다시 쓰는 것: 악보 형식과 검증(notation.js), 저장소(scores.js, 키 `ltw.scores.v2` 그대로), 악보 보기·한 줄 띠(sheet.js), 받아 적기 오선(score-input.js), 재생 예약(playback.js), 설정(settings.js), ⚙ 설정 창 방식(app.js). 형식에는 선택 필드만 더하므로 기존 악보·예시 악보는 그대로 읽힌다.
> 새 파일: `js/unzip.js`(.mxl ZIP 읽기, DecompressionStream('deflate-raw')), `js/musicxml.js`(MusicXML → 파트·보표·성부 목록, 고른 성부 → v2 악보 + 알림). 다른 파일처럼 일반 `<script>` 태그로 붙인다.
> 테스트는 ltw-test-runner로 `tests/t35.js`~`tests/t41.js`에 둔다. 테스트용 MusicXML은 테스트 파일 안의 문자열(손으로 쓴 작은 파일)과 그것을 압축한 .mxl 바이트로 두고, `File` 객체를 만들어 파일 입력에 넣는다(file://에서 fetch 없음). 실제 악보 프로그램에서 내보낸 파일 확인은 공개 MusicXML 예제(musicxml.com example set 18곡, .musicxml·.mxl)로 Claude가 한다: `python -I tests/samples/make_fixture.py`로 받아 기대값(파트·보표·성부별 음 개수 등)을 Python으로 따로 세고, `tests/samples/samples.test.js`로 앱 결과와 비교한다. 악보 파일은 사용 조건이 명시되어 있지 않아 저장소에 넣지 않는다(`tests/samples/.cache/`, .gitignore). 사용자에게 MuseScore 파일이 없어 이렇게 바꿈 (2026-10-31 사용자 요청). 🔈 소리 확인은 사용자가 같은 예제 파일(`tests/samples/.cache/xmlsamples.zip`)을 앱에서 불러와 한다.
> 36단계 전까지 불러오기 창은 파트·성부 목록까지만 보여 준다([불러오기] 버튼 잠금). 37~40단계 전까지 그 단계의 표기(새 음자리표·64분음표·겹잇단·짧은 마디 / 화음 / 꾸밈음 / 도돌이표)가 든 성부는 "아직 담지 못해요(○○)"로 불러오지 않는다. 각 단계에서 그 이유를 없앤다.
