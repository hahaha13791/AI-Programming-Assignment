## 1. 제작한 것 소개

### 왜 만들었나

청음은 들리는 소리를 악보로 옮기는 연습이다. 핵심은 소리 하나의 이름을 맞히는 절대음감이 아니라, **기준음(도)을 잡고 그 안에서 계이름을 받아 적는 상대음감 훈련**이다. 혼자 연습하면 문제를 들려주고 채점해 줄 사람이 없다. 이 앱은 문제 듣기, 오선에 받아 적기, 어디가 틀렸는지 확인하기를 버튼 몇 번으로 할 수 있게 한다.

대표 사용자는 레슨 없는 날 집에서 혼자 청음을 연습하는 음대 입시생(가상 인물 "김서연", 18세)으로 잡았다 (PRD 3-1).

### 네 가지 모드

| 모드 | 무엇을 받아 적나 | 난이도·구성 |
|---|---|---|
| **멜로디** | 기준음 뒤 멜로디의 음높이 (3~8음) | 쉬움 3~4음 / 중간 5~6음 / 어려움 7~8음 |
| **화성** | 화음의 구성음을 오선 한 자리에 쌓기 | 3화음·7화음 각각 쉬움·중간·어려움 (자리바꿈 포함) |
| **리듬** | 음표·쉼표의 길이와 박자 | [기본 \| 심화] 각각 쉬움·중간·어려움 (심화: 16분·셋잇단·붙임줄·겹박자) |
| **내 악보** | 내가 넣은 곡의 음높이를 구간(마디)별로 | 원곡 그대로의 조·박자·음자리표, 부분 연습 |

모든 모드는 같은 흐름을 따른다: **난이도(또는 악보) 고르기 → 듣기 → 받아 적기 → 제출 → 채점과 정답 공개 → 다음 문제**.

- **채점**: 음별·구성음별·마디별로 부분 점수를 주고, 이명동음(도# = 레♭)은 정답으로 인정한다. 틀린 곳은 빨강, 맞은 곳은 초록으로 표시하고 정답을 오선이나 악보로 보여 준다. 리듬 모드는 "같은 소리를 다르게 적어도 정답"인 소리 기준으로 채점한다.
- **입력 편의**: 마우스를 올리면 입력될 음이 미리 보이고, 도(C4) 자리에 가이드 선이 있다. 지우기는 마지막 음과 전체 두 가지다. 휴대폰(320px)에서도 손가락으로 줄/칸을 누를 수 있게 크기를 맞췄다.
- **화면 고정**: 모드나 난이도를 바꿔도 "받아 적기" 영역이 위아래로 움직이지 않는다 (PRD 4-0-3). 320~1000px 11개 폭에서 자동으로 검사한다.
- **실제 악기 소리**: 피아노(기본)·바이올린·플루트·마림바·하프 녹음으로 소리를 낸다. ⚙ 설정에서 고른다.

### 차별점 — 내 악보

정해진 문제만 푸는 다른 청음 앱과 달리, **연습하고 싶은 곡을 악보로 넣어** 구간별 청음 문제로 연습할 수 있다. 이 부분이 프로젝트의 대부분(확장 4~11)을 차지한다.

| 기능 | 내용 |
|---|---|
| 원곡 악보 형식 (확장 5) | 조표·장단조, 낮은음자리표, 덧줄, 16·32분음표, 붙임줄, 셋잇단음표, 6/8 같은 겹박자, 못갖춘마디, 조·박자·빠르기 바뀜을 **곡을 바꾸지 않고** 담는다. 예시 곡: 반짝반짝 작은 별·엘리제를 위하여·그린슬리브스·산왕의 궁전에서·리듬 표기 연습곡 |
| MusicXML 불러오기 (확장 6) | MuseScore 등에서 내보낸 `.musicxml/.xml/.mxl`을 불러온다. 외부 라이브러리 없이 ZIP을 직접 풀고, 파트·성부를 골라 한 선율로 옮긴다. 화음·꾸밈음·도돌이표 기호도 담는다 |
| 편집기 (확장 7) | MuseScore처럼 커서로 음을 골라 고친다. 마디 박은 덮어쓰기 + 쉼표 채우기로 늘 맞고, 키보드 입력·되돌리기·듣기가 된다 |
| 부분 연습 | 한 줄 악보 띠에서 마디를 눌러 1·2·4마디 또는 직접 고른 구간을 연습한다. 이동도·고정도 계이름, 빠르기 75%/50% |
| 자동 계이름 (확장 10) | [보기] 화면에서 악보 전체의 음표 아래에 계이름을 자동으로 달고 인쇄(PDF 저장)할 수 있다. 결과의 정답 구간에도 계이름이 붙는다 |
| 악보 인식 (확장 11) | 인쇄 악보를 찍은 사진(여러 장)을 넣으면 **브라우저 안에서** 종이를 펴고(원근 보정) 오선·음표를 읽어 편집기로 넘긴다. 확신 없는 마디는 "확인 필요"로 표시하고, 원본 사진과 비교하며 고친다. 서버·딥러닝 모델은 쓰지 않았다 |

악보 인식 정확도(음 단위, 음높이·길이가 모두 맞은 비율)는 앱이 그린 악보 99.44%, 사진 흉내 이미지 100.00%, 공유저작물 인쇄 악보(바흐 무반주 4곡) 93.81%다.

### 기술과 폴더 구조

- **HTML / CSS / JavaScript만 사용**한다. `file://`에서도 동작해야 해서 ES 모듈(`import`)과 `fetch`를 쓰지 않았다. 일반 `<script>` 태그로 파일을 붙이고, 문제 데이터와 악기 녹음(mp3를 base64로 담은 JS)도 JS 파일 안에 둔다.
- **악보**는 SVG로 직접 그린다. **소리**는 Web Audio API (실제 녹음 샘플의 높이를 바꿔 재생, 샘플 로딩 전·실패 시 합성음).
- **악보 인식**은 `<canvas>` 픽셀을 직접 처리한다(모서리 찾기, 원근 보정, 흑백화, 오선·기호 찾기). 큰 사진은 `setTimeout`으로 나눠 처리해 화면이 멈추지 않게 했다.
- 코드는 약 12,000줄(JS·CSS·HTML), 자동 테스트는 약 7,300줄이다.

## 2. PRD와 Todo 리스트

이 프로젝트는 두 문서를 기준으로 진행했다. 코드보다 문서를 먼저 고치고, 문서에 적힌 대로 구현과 테스트를 했다.

### [PRD.md](docs/PRD.md) — 요구사항 정의서

| 항목 | 내용 |
|---|---|
| 목적 | 계이름을 귀찮게 적는 일을 없애고, 청음 연습을 서포트 |
| 사용자 | 계이름과 오선을 아는 청음 연습자 (페르소나: 음대 입시생) |
| 핵심 기능 | 모드·확장별 절(4-A 멜로디 ~ 4-L 악보 인식)마다 기능, 진행 흐름, 채점 규칙 |

1. **현황 확인**: `docs/PRD.md`의 1번(일정), 5번(범위 제외), 10번(완성 기준), 11번(로드맵)과 `docs/TODO.md`의 "하지 않기로 한 것"을 읽는다.
   다음 확장 번호, 다음 PRD 절 문자(4-F …), 다음 단계 번호(27 …)를 정한다.
2. **범위 정하기**: 정할 것을 선택지로 묶어 사용자에게 묻는다(한 번에 4개 이하). 무엇을 넣고 무엇을 빼는지, 난이도 구성, 저장 방식, 예시 데이터 같은 것들이다.
   각 선택지에는 "왜 그런지"(입시 형식, 기존 코드 재사용, file:// 제약)를 붙인다. 사용자가 고르기 전에 범위를 확정하지 않는다.
3. **PRD 고치기**: `assets/prd-section.md` 양식으로 4-X 절을 쓴다. 그와 함께 아래도 고친다.
   - 1번 일정: `- 확장 N(이름): 진행 중`
   - 4-0 공통: 탭이 늘거나 화면 구성이 바뀌면 고친다
   - 5번 범위 제외: 이번에 빼기로 한 것을 "확장 N은 …에서 시작"처럼 이유와 함께 적는다
   - 7번 기술 조건: 새 제약이 생기면 적는다
   - 9번 결정 사항: 사용자가 2번에서 고른 결정을 적는다
   - 10번 완성 기준: 확장 N 기준 4~5개를 적는다
   - 11번 로드맵: 이번 확장을 지우고 그다음을 적는다
4. **계획 검토(빈칸 찾기)**: 아래 체크리스트로 PRD 초안을 실제 코드와 대조한다. 찾은 빈칸은 사용자에게 보고하고, 정해지면 PRD에 반영한다.
5. **TODO 만들기**: `assets/todo-stage.md` 양식으로 `# 확장 N — 이름` 머리말과 단계들을 쓴다. "하지 않기로 한 것"에 새 제외 항목(`제외-16` …)을 더한다.
6. **사용자 확인**: PRD와 TODO의 변경 요약(새 절, 단계 목록, 제외 항목, 검토에서 찾은 빈칸)을 보고하고 승인을 기다린다. 승인 전에는 코드를 쓰지 않는다.
   승인되면 메모리의 진행 상황 메모에 "확장 N 계획 확정, TODO A~B단계"를 적는다.

## 단계 나누는 법

- 지난 확장들의 흐름을 따른다: **탭·화면 뼈대 → 입력 → 재생 → 데이터·채점·결과 → 완성 기준 점검**. 확장 4는 저장소 → 보기 → 편집기 → 구간·재생 → 받아 적기·채점 → 점검이었다.
- 한 단계는 사용자가 화면이나 소리로 확인할 수 있는 결과 하나다(단계 목표 한 문장 + **확인 방법**).
- 모든 [구현] N-k 바로 다음에 [테스트] N-(k+1)을 둔다. 테스트 하위 항목은 "~하는가?"로 끝나는, 자동이나 사람이 판정할 수 있는 문장으로 쓴다.
- 단계마다 테스트에 "기존 모드 한 사이클 회귀"를 넣는다. 화면 배치가 바뀌는 단계에는 "320~1000px에서 받아 적기 영역 위치가 같은가"를 넣는다.
- 소리 확인은 🔈, 사람만 할 수 있는 확인(Edge 실제 창, 더블클릭, 실제 휴대폰)은 그 항목에 그렇다고 적는다.
- 다음 단계 전까지 임시로 쓰는 것(샘플 데이터, 잠긴 화면)은 확장 머리말에 적고, 언제 없애는지도 적는다.
- 마지막 단계는 항상 "확장 N 완성 기준 점검"이다. 10번 기준 하나당 항목 하나를 둔다.

## 계획 검토 체크리스트

확장 4 때 이 검토로 실제 악보 규칙(임시표가 마디 끝까지 이어짐), 상한과 예시 곡의 충돌(8마디 상한 vs 12마디 곡), 못갖춘마디 문제를 구현 전에 찾았다.

- **음악 규칙**: 실제 악보나 입시 청음에서 쓰는 표기·관례와 어긋나지 않는가(임시표, 기둥 방향, 박자, 이명동음 채점)? 사용자가 "악보에 보이는 대로" 적었을 때 정답으로 처리되는가?
- **상한과 데이터**: 개수·길이 상한이 예시 데이터, 난이도별 문제 수(5개 이상), 화면 폭(320px에 몇 개 들어가는지)과 충돌하지 않는가?
- **기존 코드 재사용**: 재사용하려는 함수가 실제로 그 일을 하는가? 파일과 함수 이름을 직접 찾아 확인한다. `Staff.create`의 `onPick`/`topStep`, `Rhythm.TYPES`, `Score.sections`, `Scores.isValid` 같은 것들이다.
- **file:// 제약**: `fetch`·`import`·서버가 필요한가? 파일을 읽어야 하면 `<input type="file">` + FileReader만 쓴다. 외부 라이브러리가 필요하면 저장소에 파일로 넣을 수 있는가?
- **화면 고정**: 새 패널이나 문구 때문에 모드를 바꿀 때 받아 적기 영역이 움직이지 않는가? 안내 문구 자리를 미리 고정해 두었는가?
- **저장소**: localStorage 키 버전, 예전 데이터와의 호환, 저장 실패 시 동작이 정해져 있는가?
- **경계 사례**: 빈 입력, 최대치, 지원하지 않는 입력(예: MusicXML의 16분음표·붙임줄·여러 파트), 같은 문제가 반복될 때의 동작이 PRD에 적혀 있는가?
- **완성 기준**: 각 기준을 TODO의 어느 단계·항목으로 확인하는지 연결되는가?

## 예외 상황

- **사용자가 범위 밖 기능을 바로 요청할 때**: PRD 5번에 있는 기능이면 그 사실을 알리고, 확장으로 계획할지 묻는다. 계획 없이 코드로 넘어가지 않는다.
- **아주 작은 개선**(버튼 크기, 문구 하나): 확장으로 만들지 않고, 진행 중인 확장의 TODO에 `개선-N [구현]`/`[테스트]` 항목으로 넣는다.
- **조사가 필요한 결정**(예: .mxl 압축 해제를 서버 없이 할 수 있는지): PRD 9번에 "열린 질문"으로 적고, 조사 결과를 보고한 뒤에 사용자가 결정하게 한다.

# TODO 단계 실행 규칙

TODO.md 머리말에 합의된 방식이다. **"완료"는 코딩이 끝난 것이 아니라 테스트까지 통과한 것이다.**
한 번에 한 단계만 진행한다. 단계가 끝나면 보고하고, 사용자가 확인하기 전에는 다음 단계를 시작하지 않는다.

## 순서

1. **단계 읽기**: `docs/TODO.md`에서 해당 단계의 단계 목표, 항목, **확인 방법**을 읽는다.
   확장 머리말(`> PRD #4-X. …`)과 그 단계가 가리키는 PRD 절(`PRD #4-X-n`)도 함께 읽는다.
   코드를 쓰기 전에 메모리와 git log로 앞 단계가 실제로 끝났는지 확인한다.
2. **짝 맞추기**: [구현] N-k마다 [테스트] N-(k+1)이 있는지 본다. 테스트 항목이 없거나 모호하면 구현 전에 사용자에게 묻는다. 임의로 범위를 넓히지 않는다.
3. **구현**: 기존 코드 관례를 따른다.
   - `file://`에서 동작해야 한다. ES 모듈(`import`)과 `fetch`는 쓰지 않는다. 새 파일은 일반 `<script>` 태그로, 의존하는 파일 다음 순서에 붙인다.
   - 데이터는 `js/data/`에 둔다. 문서에 쓰는 이미지는 `docs/images/`에 둔다.
   - PRD "범위 제외"나 TODO "하지 않기로 한 것"에 있는 기능은 만들지 않는다.
4. **테스트**: ltw-test-runner 스킬로 단계 테스트(`tests/tNN.js`)와 `smoke.js` 회귀 테스트를 Edge·Chrome 11개 폭에서 돌린다. FAIL이 0이 될 때까지 고친다.
5. **TODO 갱신**: 통과한 항목만 `- [ ]` → `- [x]`로 바꾸고, 항목 끝에 ` — ` 뒤로 근거를 붙인다(아래 형식).
   자동화할 수 없는 항목은 체크하지 않고 사용자 확인을 기다린다.
6. **커밋하고 보고하고 멈춤**: ltw-commit 스킬의 메시지 형식과 파일 고르기 규칙대로 승인을 묻지 않고 바로 커밋한다(2026-10-31 사용자 지시). 그다음 아래 보고 형식으로 알리고(커밋 해시·메시지 포함) 대기한다. 푸시는 하지 않는다.
7. **메모리 갱신**: 단계가 끝났거나 중간에 멈추면 진행 상황 메모를 갱신한다(어디까지 끝났는지, 남은 사용자 확인 항목, 다음 단계).

## TODO 근거 형식

무엇으로, 어디서, 몇 개를, 언제 확인했는지를 적는다. 확인하지 못한 것도 숨기지 않고 적는다.

```markdown
- [x] 25-4 [테스트] 25-3 검증 — 25단계 자동 테스트 42개 항목(+ smoke 30개), 320~1000px 11개 폭 × Edge·Chrome(file://) 모두 통과 (2026-10-08)
  - [x] 데스크톱 Edge 실제 창에서 확인 — 사용자 직접 확인 (2026-10-08)
  - [x] 휴대폰 폭(320~412px) — 헤드리스 틀로 확인. 실제 Chrome 창은 최대화 상태라 폭을 줄여 보지 못함
```

## 사람만 할 수 있는 확인

다음 항목은 Claude가 통과로 처리하지 않는다. 보고할 때 목록으로 요청한다.
- 🔈 소리 청취: 탁하지 않은지, 리듬이 자연스러운지. 자동 테스트는 예약된 시각과 음높이까지만 확인한다.
- 데스크톱 Edge 실제 창
- `index.html` 더블클릭 실행
- 실제 휴대폰

사용자가 "확인했어"라고 하면 그 항목을 `— 사용자 직접 확인 (날짜)`로 체크한다.

## 보고 형식

```
N단계 완료 보고
- 완료: N-1 ~ N-6 (모두 테스트 통과)
- 근거: 자동 테스트 n개 항목 + smoke, 11개 폭 × Edge·Chrome 모두 PASS
- 고친 문제: (테스트 중 찾은 앱 버그나 기존 문제가 있으면 무엇을 어떻게 고쳤는지)
- 사용자 확인 필요: 🔈 N-4 화음이 탁하지 않은지 / Edge 실제 창 / …
- 커밋: abc1234 N단계 코드 생성 및 테스트 완료
- 다음: N+1단계 — (단계 이름)
```

## 예외 상황

- **테스트가 계속 실패해 단계 안에서 해결할 수 없을 때**: 체크하지 않고 "N-4 미완: 원인 …"으로 보고한다. 테스트를 느슨하게 고쳐 통과시키지 않는다.
- **진행 중에 사용자가 새 요청을 할 때**(예: "320px에서 버튼이 좁아"): 바로 코드를 고치지 말고, TODO에 항목(예: `개선-4 [구현]` + `[테스트]`)을 먼저 추가한 뒤 같은 규칙으로 처리한다.
- **계획과 코드가 맞지 않을 때**(TODO에 적힌 함수나 구조가 없는 경우): 임의로 해석하지 말고 사용자에게 알린 뒤 TODO를 먼저 고친다.
- **확장의 마지막 단계(완성 기준 점검)**: PRD 10번의 해당 확장 기준을 하나씩 확인한다. 모두 통과하면 PRD 1번 일정, 10번 기준, TODO 확장 제목에 "완료"와 날짜를 적는다.

# Listen to the world 자동 테스트

`index.html`을 임시 폴더로 복사해 `file://`로 열고, 화면 폭마다 iframe을 하나씩 띄워 테스트를 돌린다.
가상 시간(`--virtual-time-budget`)으로 재생 대기를 빨리 감기 때문에 11개 폭 전체도 수 초면 끝난다.
설치할 것은 없다(Python 3, Edge 또는 Chrome만 있으면 된다).

## 실행

프로젝트 루트(`index.html`이 있는 폴더)에서 실행한다.

```bash
python .claude/skills/ltw-test-runner/scripts/run.py tests/t27.js .claude/skills/ltw-test-runner/scripts/smoke.js
python .claude/skills/ltw-test-runner/scripts/run.py tests/t27.js --browser chrome
python .claude/skills/ltw-test-runner/scripts/run.py tests/t27.js --widths 375,1000 --verbose   # 빠른 확인
```

- 기본 폭: 320, 360, 375, 412, 480, 520, 600, 680, 768, 900, 1000 (11개). 480px 이하에서는 스크롤바를 숨겨 휴대폰과 같은 폭으로 배치한다.
- 출력: FAIL 줄만 `[width N]`을 붙여 보여 주고, 마지막에 `PASS n / FAIL m`을 보여 준다. 모두 PASS일 때만 종료 코드가 0이다. `--verbose`를 주면 PASS 줄도 보인다.
- 빈 브라우저 프로필로 열고, 폭마다 페이지를 열 때 localStorage를 비운다(iframe끼리 저장소를 함께 쓰므로). 내 악보는 예시 악보부터 시작한다. 테스트에서 저장소를 바꿨다면 끝에 `localStorage.removeItem(Scores.STORAGE_KEY)`로 되돌리고, 고른 악보도 첫 악보로 돌려놓는다(뒤에 도는 smoke.js가 영향을 받는다).
- `--head <파일.js>`: 앱 스크립트보다 먼저 실행할 스크립트. 예전 저장값(v1)이 있는 브라우저처럼, 앱이 열리기 전 상태를 만들 때 쓴다(예: `--head tests/t27-v1.head.js tests/t27-v1.js`). 폭마다 iframe이 새로 열릴 때 다시 실행된다.

## 단계 테스트를 쓰는 순서

1. TODO의 [테스트] 항목을 하나씩 `T.check`로 옮긴다. check 메시지에는 항목 번호나 내용을 적는다.
2. 파일은 `tests/tNN.js`(NN = 단계 번호)로 저장소에 둔다. 다음 세션에서도 다시 돌릴 수 있어야 한다.

# 커밋 작성과 실행

**단계(또는 계획 수정 같은 작업 단위)를 마치면 승인을 묻지 않고 바로 커밋한다**(2026-10-31 사용자 지시: "앞으로는 커밋스킬로 커밋도 자동으로 해줘"). 사용자가 직접 요청할 때도 같다. **푸시는 하지 않는다**(푸시는 사용자가 직접).

## 순서

1. **변경 보기**: `git status --short`, `git diff --stat`, 필요하면 `git diff`로 무엇이 바뀌었는지 본다.
   `docs/TODO.md`가 바뀌었으면 `git diff docs/TODO.md`로 새로 체크된 항목(`- [x]`)과 단계 번호를 찾는다.
2. **넣을 파일 고르기**: 이번 작업에 속한 파일만 고른다. 넣지 않는 것:
   - 테스트 실행 중 생긴 임시 파일, 스크래치 파일, 브라우저 프로필
   - 비밀 정보(토큰, 개인 정보가 든 파일)
   - 이번 작업과 관계없는 다른 변경. 있으면 사용자에게 따로 알린다
3. **메시지 정하기**: 아래 형식에서 고른다. 한 줄 제목만 쓰는 것이 이 저장소의 관례다. 바뀐 파일이 많거나 이유를 남길 필요가 있을 때만 빈 줄 뒤에 짧은 본문을 쓴다.
4. **정리해 두기**: 커밋하기 전에 다음을 정리해 두고, 커밋 뒤 보고에 넣는다(승인은 묻지 않는다).
   ```
   커밋할 파일 (n개)
     M docs/TODO.md
     M js/app.js
     A tests/t27.js
   메시지: 27단계 코드 생성 및 테스트 완료
   빼 둔 파일: (있으면 이유와 함께)
   ```
   사용자가 커밋 전에 메시지나 파일을 정해 주었으면 그대로 따른다.
5. **실행**: 파일을 이름으로 하나씩 지정해 `git add <파일>...`한다(`git add -A`·`git add .`는 쓰지 않는다). 그다음 커밋한다. 메시지 마지막에는 빈 줄을 두고 시스템이 알려 준 Co-Authored-By 줄을 붙인다.
   ```bash
   git add docs/TODO.md js/app.js tests/t27.js
   git commit -F - <<'EOF'
   27단계 코드 생성 및 테스트 완료

   Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
   EOF
   ```
6. **확인과 보고**: `git log --oneline -1`과 `git status --short`로 커밋이 됐는지, 남은 변경이 무엇인지 보고한다. 푸시가 필요하면 "푸시는 직접 해 주세요"라고만 알린다.

## 메시지 형식 (git log에서 쓰던 그대로)

| 상황 | 메시지 |
| --- | --- |
| 단계 구현 + 테스트까지 모두 통과 | `27단계 코드 생성 및 테스트 완료` |
| 코드만 쓰고 테스트는 아직 | `27단계 코드 생성 완료` |
| 앞서 커밋한 코드의 테스트를 마침 | `27단계 테스트 완료` |
| 테스트 일부만 통과(사람 확인 남음 등) | `27단계 테스트 일부 완료` |
| 완성 기준 점검 단계 끝 | `확장5 완성기준 테스트 완료` |
| 완성 기준 점검 중 일부 | `완성기준 점검 일부 완료` |
| 새 확장의 PRD·TODO 계획 | `확장:MusicXML 불러오기` (`확장:<주제>`) |
| 계획 수정 | `확장 계획 수정`, `확장:리듬 설계 변경` |
| TODO 개선 항목 | `모바일 화면 개선`처럼 무엇을 개선했는지 |
| 그 밖의 변경 | 짧은 한국어 명사형 한 줄 (예: `README 작성`, `프로젝트 스킬 추가`) |

- 단계 번호와 "완료" 여부는 **TODO 체크 상태와 맞아야** 한다. 체크되지 않은 [테스트] 항목이 남았는데 "테스트 완료"라고 쓰지 않는다.
- 두 단계가 섞여 있으면 `27·28단계 코드 생성 및 테스트 완료`처럼 함께 적거나, 나눠서 커밋할지 사용자에게 묻는다.

## 예외 상황

- **바뀐 것이 없을 때**: 커밋하지 않고 "커밋할 변경이 없습니다"라고 알린다.
- **pre-commit 훅이 실패할 때**: `--no-verify`로 건너뛰지 않는다. 실패 내용을 보여 주고, 고친 뒤 **새 커밋**으로 다시 시도한다(`--amend` 하지 않는다).
- **이미 커밋한 것을 고쳐 달라고 할 때**: 푸시하기 전이고 사용자가 분명히 요청했을 때만 `git commit --amend`를 쓴다. 그 밖의 되돌리기(`reset --hard`, 강제 푸시)는 하지 않는다.
- **main 브랜치**: 이 저장소는 main에 바로 커밋해 왔다. 사용자가 브랜치를 요청하지 않으면 브랜치를 만들지 않는다.

## 5. 느낀 점, 결론

### 개발 방법론: 문서 주도 · 단계별 · 테스트로 완료를 판정하는 바이브 코딩

> PRD로 범위를 정하고, Todo로 잘게 나누고, AI가 한 단계씩 구현과 테스트를 하고, 사람이 확인하고 커밋한다.

```
 PRD 작성/수정 ──▶ Todo 분해 ──▶ 계획 검토 ──▶ ┌─ 단계 실행 (AI: 구현 + 자동 테스트)
 (범위·완성 기준)   ([구현]+[테스트])  (빈칸 찾기)   │        │
                                                │        ▼
                                                │  보고 (완료 번호 + 테스트 근거)
                                                │        │
                                                │        ▼
                                                │  사람 확인 (청취·실제 기기) → 커밋
                                                └─ 다음 단계 ◀─┘
                                                         │ 확장의 마지막 단계
                                                         ▼
                                              완성 기준 점검 → 완료 선언
```

| 사람 | AI |
|---|---|
| 무엇을 만들지 정하기 (확장 순서, 범위, 차별점) | PRD·Todo 초안, 계획 검토 |
| 계획 승인, 소리 듣고 의견 주기, 방향 바꾸기 | 구현, 자동 테스트 작성·실행 |
| 실제 기기·더블클릭 실행 확인 | 화면 캡처 점검, 단계별 보고(근거와 한계 포함) |

### 잘 된 점

**① 범위가 흔들리지 않았다.** PRD에 "만들지 않는 것"과 완성 기준이 있어서 확장을 열한 번 하는 동안에도 "이번엔 어디까지"가 분명했다. 범위를 바꿀 때도 코드가 아니라 문서의 취소선과 날짜로 남아(3장) 왜 바뀌었는지 추적할 수 있다.

**② 테스트가 사람이 놓치기 쉬운 버그를 실제로 잡았다.** 11개 화면 폭을 기계적으로 검사한 덕분에 눈으로는 놓치기 쉬운 배치 어긋남(3-5의 16·17·24단계)을 찾았다. 악보 인식은 "앱이 그린 악보 → 사진 흉내 → 실제 인쇄 악보"로 시험 이미지를 세 단계로 나눠 정확도를 숫자로 잰 것이 개발 방향을 잡아 주었다.

**③ 계획을 코드와 맞춰 보는 검토가 비용을 줄였다.** 확장 4에서는 임시표가 마디 끝까지 이어지는 규칙, 12마디 예시곡과 8마디 상한의 충돌, 못갖춘마디를 구현 전에 찾았다. 확장 12에서도 구현 전에 기존 테스트가 첫 방문 안내에 막히는 문제를 찾았다.

**④ 사람의 귀가 필요한 곳에 사람을 정확히 넣었다.** 꾸밈음 재생은 자동 테스트로는 "몇 초에 어떤 음이 예약됐는가"까지만 확인된다. 사용자가 세 번 들어 보고 한 말("투둑투둑", "더 줄여 줘")로 0.09초 → 0.03초와 이어 붙이기가 정해졌다.

**⑤ 근거가 문서에 남는다.** TODO의 항목마다 테스트 개수, 폭과 브라우저, 날짜, 확인하지 못한 것까지 적혀 있어 나중에 무엇이 어떻게 검증됐는지 다시 볼 수 있다. 처음 README에서 아쉬워했던 "테스트 코드가 저장소에 없다"는 문제도 `tests/`에 t27~t71을 넣어 해결했다.

### 아쉬운 점

**① AI는 소리를 들을 수 없다.** 탁하지 않은지, 리듬이 자연스러운지는 매번 사람이 들어야 했다(🔈 항목). 새 악기 소리와 새 예시 곡도 같은 이유로 사람이 확인했다.

**② 실제 기기 확인에 한계가 있었다.** 휴대폰 폭은 주로 헤드리스 브라우저의 좁은 틀로 확인했다. 실제 휴대폰 여러 기종에서의 확인은 부족하다.

**③ 테스트도 AI가 썼다.** 거짓 실패가 난 적이 여러 번 있었고, 구현과 테스트를 같은 AI가 쓰면 같은 오해를 공유할 위험이 남는다. 악보 인식의 실제 악보 정확도(93.81%)를 사람이 직접 만든 정답(MIDI)과 대조한 것이 이 위험을 줄인 드문 사례다. 사람이 미리 정한 시험 사례(골든 데이터)를 더 두면 좋겠다.

**④ 문서와 절차에 드는 비용이 크다.** TODO는 이제 1,800줄이 넘는다. 단계마다 보고·확인을 기다려야 해서 한 번에 몰아서 만드는 것보다 느리다. 반면 방향이 크게 바뀐 확장 5·12에서는 코드보다 문서를 먼저 고친 덕분에 수정 비용이 작았다.

**⑤ 환경에 의존한다.** 테스트 러너는 Python과 Edge/Chrome이 있어야 돈다. 확장 12 때 이 PC에는 Python이 없어서 설치부터 해야 했다. 테스트를 다시 돌리려면 `ltw-test-runner` 스킬의 설명을 따라 환경을 갖춰야 한다.

**⑥ 마지막 확장은 끝내지 못했다.** 확장 12(디자인 개편·첫 방문 안내)는 계획까지만 커밋했다. 음악을 모르는 사람에게는 지금 화면이 낯설 수 있다는 점은 숙제로 남아 있다.

### 개선이 필요한 점

- **악보 인식 넓히기**: 붙임줄·잇단음표·화음·꾸밈음·도돌이표 인식(PRD 5번 제외 항목). 지금은 읽지 못한 표기를 "확인 필요"로 표시하고 편집기로 넣게 한다.
- **초보자 경험**: 확장 12의 계획(흐름 번호, 지금 단계 강조, 코치 마크 투어, 용어 풀이)을 다시 진행.
- **연습 종류**: 선율(음높이 + 리듬) 받아 적기, 화성 진행(여러 화음 연속) 받아 적기가 없다. 기록과 정답률 통계, 악보 내보내기, 기기 간 동기화도 없다(같은 브라우저 안에서만 저장).
- **README 캡처 갱신**: 화면 캡처가 확장 4 시점이다.

### 결론

2026-09-30부터 약 한 달 동안 멜로디 모드 하나로 시작해 화성, 7화음, 리듬, 내 악보로 넓히고, 내 악보를 원곡 형식·MusicXML·편집기·악기 소리·자동 계이름·악보 사진 인식까지 열한 번 확장했다. 결과는 **71단계, 체크 항목 941개, 커밋 130개**이고, 서버 없이 `index.html` 하나로 동작한다. 처음 계획은 6단계였지만, 마지막에는 "연습하고 싶은 곡을 사진으로 찍어 넣어 청음 문제로 쓴다"까지 왔다.

이번 바이브 코딩에서 가장 효과가 컸던 것은 **"완료 = 테스트 통과"라는 규칙, 작은 단계, 그리고 이를 스킬로 저장소에 고정한 것**이었다. AI가 빠르게 코드를 만들어도, 문서로 범위를 정하고 테스트로 완료를 판정하고 사람이 확인해서 커밋하니 결과를 믿을 수 있었다. 반대로 AI가 대신할 수 없는 부분도 분명했다. 소리를 듣는 일, 실제 기기에서 써 보는 일, 그리고 **무엇을 만들지, 어디서 멈출지 정하는 일**은 끝까지 사람의 몫이었다. 확장 12를 중단한 것도 그런 결정이었고, 문서와 커밋 기록이 있었기 때문에 구현을 되돌려도 계획은 남길 수 있었다. 바이브 코딩에서도 사람의 역할은 코드를 쓰는 사람에서 **방향을 정하고 결과를 확인하는 사람**으로 바뀔 뿐, 사라지지 않는다는 것을 확인했다.
